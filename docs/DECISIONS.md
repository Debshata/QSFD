# Engineering Decisions

Judgement calls made during the unattended build of the fraud-detection layer,
with the reasoning behind each. Where a decision constrains what the results
can be claimed to show, that is stated.

---

## Data

### D1. A dataset registry, not four preprocessing functions

The four Kaggle sources have four incompatible schemas. Rather than branch on
dataset name throughout the pipeline, `src/data/registry.py` normalises each
into a common `DatasetSpec` (features + binary target + column roles). Column
roles come from explicit config first and name/cardinality heuristics second,
so an unseen fifth dataset still gets a defensible answer.

### D2. `creditcardfraud` is the primary dataset

`config/datasets.yaml: primary_dataset` selects the dataset the production
model is trained on. `mlg-ulb/creditcardfraud` was chosen because its 0.173%
fraud rate is the only realistic base rate of the four:

| Dataset | Fraud rate | Why not primary |
|---|---|---|
| `creditcardfraud` | 0.173% | **selected** |
| `fraud_detection_sim` | 1.50% | usable; simulated merchant metadata |
| `creditcard_2023` | 50.0% | balanced by construction, not a base rate |
| `synthetic_cc_fraud` | 13.1% | features generated by the same process as the labels |

All four are still profiled, validated and reported. Any of them can be
trained on with `--dataset`.

### D3. Identifier and high-cardinality columns are dropped

`cc_num`, `trans_num`, `first`/`last`, `street`, `id`, `user_id` identify a
person, a card or a row. Keeping them lets a tree memorise individuals instead
of learning fraud, and none of them generalise to a new customer. Free-text
`merchant`, `city` and `job` exceed the cardinality cap (60) and are dropped;
`state` (50 values) is under the cap and is kept as a categorical.

### D4. Duplicates are removed before splitting, not after

`creditcardfraud` contains 9,144 exact duplicate rows (3.2%). If a duplicate
pair straddles the train/test boundary, the model has literally memorised the
test row and every metric is inflated. Deduplication therefore happens in
`drop_cross_split_duplicates` **before** any split. Rows are compared on
features *and* label, so a genuinely ambiguous duplicate (same features,
conflicting labels) is kept rather than silently resolved.

### D5. Temporal split where the data is chronological

`creditcardfraud` rows are ordered by `Time`. In deployment you always predict
forward in time, so a random split overstates performance. The pipeline uses a
temporal split when the source is ordered and a time column exists, and falls
back to a stratified random split otherwise -- or when a temporal split leaves
a fold with zero fraud cases, which would make that fold useless.

This is the main reason the reported test metrics are lower than the numbers
usually quoted for this dataset: a random split on `creditcardfraud` typically
reports PR-AUC around 0.87, a temporal split does not.

### D6. `Time` is not a feature

It is seconds since the first transaction in the file -- an index, not a
property of the transaction. It orders the temporal split and is then dropped.

## Modelling

### D7. No hyperparameter search

Explicitly out of scope per the brief. Every model uses fixed strong defaults
in `config/classical.yaml`. A tuned model would very likely score somewhat
higher; that is stated as a limitation in the final report rather than papered
over.

### D8. Class weighting as the default imbalance strategy

`class_weight` / `scale_pos_weight` is the default because it is the simplest
defensible option, adds no synthetic rows, and cannot leak. SMOTE and
undersampling are implemented and configurable, and both are applied to the
training fold only, inside `apply_imbalance`, which is never called with
validation or test data.

### D9. Isolation Forest is kept separate from the supervised models

It never sees a label. Its `score_samples` output is an anomaly rank, not a
fraud probability. It is:

- excluded from production-model selection (the risk engine needs a probability),
- flagged `score_is_probability = False` everywhere,
- reported with a note that its PR-AUC is not comparable to the supervised models,
- given no per-feature attribution, because there is no honest one to give.

Its measured PR-AUC of 0.04 against 0.82 for Random Forest is exactly what
unsupervised anomaly detection looks like on this problem, and is reported as
such rather than hidden.

### D10. Thresholds are chosen on validation with an F2 objective

0.5 is meaningless at a 0.17% base rate. `select_threshold` searches a
quantile grid (a uniform grid puts nearly every candidate above the mass of
the score distribution) on the **validation** fold. F2 is the default because
a missed fraud costs more than a false alarm; `max_recall_at_precision` and
`max_precision_at_recall` are available for an explicit analyst-workload cap.
The test fold never influences the threshold.

### D11. Calibration is kept only when it helps

Downstream risk banding consumes a probability, so calibration matters.
Platt/sigmoid calibration is fitted on validation via `FrozenEstimator`, so
the base model is not refitted on the validation fold. It is retained only if
it improves the validation Brier score. When calibration is applied the
threshold is re-selected, because calibration changes the score scale.

### D12. Model selection is a published weighted score, including latency

`config/classical.yaml: selection.weights` -- PR-AUC 0.45, recall 0.20,
F2 0.15, precision 0.10, latency 0.10, minus a false-positive penalty. The
full candidate table is written into `final_evaluation.md`, so the choice can
be audited or overridden rather than taken on trust.

### D12a. Latency is measured per single transaction, not per batch row

The first implementation timed inference over the whole 55k-row test fold and
divided. That figure is batch throughput, and it hid a 60x difference between
candidates:

| Model | PR-AUC | Batch (ms/row) | **Single transaction (ms)** |
|---|---:|---:|---:|
| Random Forest | 0.819 | 0.005 | **59.18** |
| XGBoost | 0.801 | 0.001 | **3.22** |
| Logistic Regression | 0.733 | 0.0001 | **0.77** |

A 300-tree forest amortises beautifully across 55k rows and costs ~59 ms on
one row -- which is exactly what an online fraud API does. `train.py` now
benchmarks single-row scoring explicitly, and selection uses that number via a
latency-quality term (1.0 at <=1 ms, decaying to 0 at 100 ms).

**Consequence:** the production model changed from Random Forest to XGBoost.
XGBoost gives up 0.018 PR-AUC (0.801 vs 0.819) and 0.014 recall for an 18x
latency improvement. For a real-time transaction path that is the better
trade; both models remain persisted, and reweighting `selection.weights`
reverses the choice without a code change.

### D13. SHAP is optional

SHAP gives the best tree attribution available, but an explainability library
that fails to import must not take the fraud engine down. `shap_available()`
caches a single guarded import, and the explainer falls back to native
importance weighted by the transaction's own feature values.

## Risk

### D14. Probability and risk level are separate concepts

The model produces a probability; the LOW/MEDIUM/HIGH mapping is a business
decision living in `config/risk.yaml`. Both are returned. Nothing in `src`
hardcodes a band.

### D15. A flagged transaction is floored at MEDIUM

The two concepts can disagree: Random Forest's selected threshold is ~0.04,
well inside the LOW band (p <= 0.30). Reporting LOW for a transaction the
model just flagged would hide a positive detection from the security layer.
`enforce_threshold_floor` lifts such a transaction to MEDIUM, and the
behaviour is configurable.

## Quantum ML

### D16. QML is an experimental parallel branch

The classical model is the production path. QML runs on a statevector
simulator at a few hundred samples; nothing about its measured performance or
runtime justifies putting it on a real-time path.

### D17. 4 qubits, PCA to 4 components

29 features cannot enter a simulated circuit directly. PCA to 4 components
(85.8% variance retained on `creditcardfraud`) keeps simulation tractable and
sits in the 4-8 range the brief specifies. The reducer and the [0, pi] angle
scaler are fitted on the QML training subset only; validation and test are
transformed and clipped.

### D18. The QML subset is deliberately rebalanced

Sizes (250 / 100 / 200) were set from a measured benchmark: the fidelity
quantum kernel needs O(n^2) circuit evaluations, ~170 pairs/s on this machine.
At the real 0.17% base rate, 250 samples would contain zero fraud cases, so
the subset is drawn at a 30% fraud ratio.

**Consequence:** QML metrics are comparable only to the controlled classical
baselines on the identical subset, never to the full-scale classical
benchmark. This is stated in the final report and in the CSV headers.

### D19. Controlled comparison uses identical everything

Logistic regression, RBF-kernel SVM and random forest are retrained on exactly
the same reduced features and the same subset folds. Without that, any
classical-vs-QML statement would be comparing two different problems. The RBF
SVM is the direct classical counterpart to the quantum kernel.

### D20. QML scores are labelled as scores, not probabilities

- **QSVM** returns a signed SVM margin. `probability=True` would need an
  internal CV refit, multiplying an already-quadratic kernel cost, for a
  poorly-supported probability. We report the margin and label it a score.
- **QNN** returns an expectation value in [-1, 1]. It is mapped monotonically
  to [0, 1] for plotting only -- ranking is unchanged, so ROC-AUC and PR-AUC
  are unaffected -- and flagged `score_is_probability = False`.
- **VQC** uses a soft-max readout, so its class-1 output *is* a probability
  and is labelled as one.

Nothing fabricates a probability a model cannot support.

### D21. Qiskit 2.x API resolution

Qiskit 2.x replaced `ZZFeatureMap` with `zz_feature_map`. `src/qml/circuits.py`
resolves the config name against whatever the installed version provides, so
the same config works on 1.x and 2.x. Verified against qiskit 2.5.2 /
qiskit-machine-learning 0.9.0 / qiskit-aer 0.17.2 on Python 3.14.

## Operations

### D22. Stage-level checkpointing

Each pipeline stage records a fingerprint of the config files it depends on
plus its expected outputs. A stage is skipped when both are unchanged. An
unattended re-run after a QML failure does not retrain the classical models.

### D23. Optional stages cannot sink the run

`train_qml` is marked optional: its failure is recorded with a traceback and
surfaced in the final report, and later stages still run. Within it, each
model is isolated, so a QNN failure does not lose a trained QSVM.

### D24. The smoke test loads from disk

`src/fraud_engine/demo.py` reloads the persisted artifacts rather than reusing
an in-memory object, which is the only way to prove the artifacts are actually
reusable by the security layer.
